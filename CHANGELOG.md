# Changelog

All notable changes to this project are documented here. This project forked from [`@daytona/opencode`](https://github.com/daytona/integrations/tree/main/packages/opencode-plugin); upstream history up to version 0.192.0 is visible [there](https://github.com/daytona/integrations/blob/main/packages/opencode-plugin/CHANGELOG.md).

## [0.1.0] - 2026-08-26

Initial fork release, based on `@daytona/opencode` 0.192.0.

### Added

- Plugin `apply_patch` tool (found during issue #11 verification): opencode 1.18+ force-enables its built-in patch tool for GPT-5-family models, and that builtin edits the local checkout, bypassing the SSH transport. The plugin now shadows `apply_patch` with its own tool implementation that applies the patch on the machine over SSH, mirroring the builtin's behavior — parser (Add/Delete/Update File sections, `*** Move to:`, `@@ context` anchors), four-tier fuzzy line matching (exact / trimEnd / trim / unicode-punctuation-normalized, with the trailing-empty-line retry; the builtin's `*** End of File` anchor is inert there, so it is kept inert here for parity), all-reads-then-writes sequencing (a failing hunk writes nothing; moves write the destination before removing the source), error messages, and the `Success. Updated the following files:` output — while every read/write/delete runs over SSH in the session workspace. No LSP diagnostics or formatter hooks run on the remote machine, so those builtin post-edit steps are omitted. `plugins/system-transform.ts` additionally instructs the model that file tools (including the plugin's `apply_patch`) operate on the machine and to never edit the local checkout directly.
- `REMOTE_*` configuration resolution (`REMOTE_HOST`, `REMOTE_PORT`, `REMOTE_USER`, `REMOTE_PROJECT_PATH`, `REMOTE_SSH_KNOWN_HOSTS`) with `.env` support in the project root; process env takes precedence (issues #1, #2)
- SSH transport core (`core/ssh.ts`): `SshExecutor` runs commands over the system `ssh` binary (honoring `~/.ssh/config`, keys, agents, jump hosts) with ControlMaster connection reuse and keepalive probes that drop dead connections within ~45s; when `REMOTE_SSH_KNOWN_HOSTS` is set, command execution pins host-key verification to that file (same semantics as git transfers). Also exports `shellQuote` and `sshCommonArgs` helpers (issue #3)

### Removed

- `@daytona/sdk` dependency: nothing in the plugin imports the SDK anymore, so installs no longer pull it (found during issue #9)

### Changed

- All tools rewritten onto the SSH transport and `getPreviewURL` deleted (issue #8): every tool's `execute` resolves the session's `RemoteSession` handle via `getRemoteSession` and runs POSIX commands (`cat`, `ls`, `find`, `grep`, `mkdir` — no `rg`/`fd` assumption) through `SshExecutor` with the session workspace as cwd; all paths interpolated into remote commands go through `shellQuote`. `bash` runs foreground commands reporting `Exit code: N` plus stdout (stderr appended when non-empty), and background commands via `nohup sh -c … > log 2>&1 & echo $!` with a client-generated `/tmp/opencode-remote-<sessionId>-<timestamp>.log` path, returning the pid and log path; `read`/`write`/`edit`/`multiedit` use `cat` reads and stdin writes (`mkdir -p` before writes, `dirname` computed POSIX-locally), with `edit`/`multiedit` keeping their exact validation logic (non-empty `oldString`, exactly-one-occurrence / per-edit sequential replacement); `ls` defaults to the session workspace and lists with `ls -1A`; `glob` shells out to `find . -type f -name`; `grep` uses `grep -rnI` (exit 1 → "No matches found", results truncated at 100 matches with the refine-your-pattern note). `gitSync` takes `branchNumber` and workspace paths off the session handle and keeps the enqueue + result-message flow. Tool descriptions say "remote machine" instead of "Daytona sandbox"; Zod argument shapes are unchanged. `RemoteSessionManager` gains a public `getSshExecutor(worktree)` so tools share the lazily-resolved config/executor pair.
- Git layer migrated to the SSH/bare-repo design (issue #5): `git/host-git-manager.ts` reads `REMOTE_SSH_KNOWN_HOSTS` instead of `DAYTONA_SSH_KNOWN_HOSTS`, now always sets `GIT_SSH_COMMAND` for transfers (BatchMode + connection reuse via `core/ssh` helpers; host-key pinning appended only when `REMOTE_SSH_KNOWN_HOSTS` is set), uses `opencode-remote@localhost` for reservation commits, and gains `removeRemote()`; `git/sandbox-git-manager.ts` renamed to `remote-git-manager.ts` with `RemoteGitManager` (no SDK types) running git over `SshExecutor` in the remote workspace and transporting commits through a per-session bare repository (`initFromBare`, `ensureBareRepo`, `pushToBare`).
- `SessionGitManager` rewired onto the SSH transport (issue #6): the constructor now takes the session's `SshExecutor` plus the workspace and bare-repo paths (no `Sandbox`), composing `RemoteGitManager` + `HostGitManager`; the host git remote points at the per-session bare repository, `initializeAndSync()` seeds the remote workspace via `ensureBareRepo`/`initFromBare`, and `autoCommitAndPull()` force-pushes the workspace to the bare repo (`pushToBare`) before the host pull. `HostGitManager` receives the resolved known-hosts file through `SshExecutor.knownHosts` (constructor parameter, `process.env` fallback preserved), so a `REMOTE_SSH_KNOWN_HOSTS` set only in `.env` pins git transfers the same as command execution.
- `core/session-manager.ts` rewritten as `RemoteSessionManager` (issue #7): all `@daytona/sdk` usage and sandbox create/start/refresh/404-reconnect logic removed; `getSandbox` becomes `getRemoteSession`, returning a `RemoteSession` handle (`workspacePath`, `bareRepoPath`, `branchNumber`) resolved from the in-memory cache or storage — storage hits are reconnected over SSH (`mkdir -p` + `ensureRepo`, with recovery via the init flow when the workspace lost its `.git` remotely), and new sessions allocate a number via the local `opencode/N` refs (falling back to the highest numeric entry under `REMOTE_PROJECT_PATH` plus one when git is disabled) before running `SessionGitManager.initializeAndSync`. The constructor takes only the storage dir; the `RemoteConfig`/`SshExecutor` pair is resolved lazily per worktree and a missing `REMOTE_HOST`/`REMOTE_PROJECT_PATH` fails with a config error toast (the old `DAYTONA_API_KEY` failure mode). `deleteSandbox` becomes `deleteSession`: after one best-effort final sync it removes only local state (memory handle, stored mapping, `sandbox-N` git remote) — nothing on the remote machine is ever deleted; a failed final sync no longer blocks deletion. Kept: deletion tombstone + dedup, `ensureNotDeleted` post-await guard, `setProjectContext`/`loadProjectSessions` cache hydration (now storing `RemoteSession` handles), cross-project migration via `getSession`; `hasSandbox` renamed to `hasSession` and `getBranchNumberForSandbox` deleted (handles carry `branchNumber`).
- Session storage schema tracks the remote workspace instead of a sandbox: `SessionInfo.sandboxId` renamed to `workspacePath`, `SandboxInfo`/`SessionSandboxMap` and the `@daytona/sdk` import removed from `core/types.ts`, new `RemoteSession` in-memory session handle type, and `getBranchNumberForSandbox` renamed to `getBranchNumberForWorkspace` in `core/project-data-storage.ts` (issue #4)
- Plugin wiring migrated and the build made green end-to-end (issue #9): the entry module (`remote/index.ts`) logs to `opencode/log/remote.log`, stores session state under `opencode/storage/remote`, constructs `RemoteSessionManager` with only the storage dir (remote config resolves lazily), drops the hardcoded repo path and all `DAYTONA_*` references, re-exports the new `core/types.ts` type surface, and exports `remotePlugin` (renamed from `daytonaPlugin`); the 60s-bounded `dispose` drain is unchanged. `plugins/custom-tools.ts` calls `createRemoteTools`; `plugins/session-events.ts` handles `session.deleted` via `deleteSession` (toasts: "Session removed — remote files left untouched on <host>", "Delete failed") and keeps the synchronous idle-sync queue shape (tombstone re-check inside the queue entry, `getRemoteSession`, `branchNumber` from the session handle, `SessionGitManager.autoCommitAndPull`, errors logged only); `plugins/system-transform.ts` pushes a "## Remote Machine Integration" block that names the resolved host when the config resolves (generic text otherwise) and describes the numbered workspace under `REMOTE_PROJECT_PATH`, background commands, `ssh -L` tunnels for dev servers, and the `gitSync` handoff
- Repositioned as `opencode-remote-plugin`: runs OpenCode sessions on any SSH-reachable machine instead of Daytona sandboxes (documentation updated)
- Package renamed from `@daytona/opencode` to `opencode-remote-plugin`; metadata points to this repository; `author` dropped (Apache-2.0 + README credits retained) and `@opencode-ai/plugin` aligned to `1.18.23` in both manifests (issue #10)
